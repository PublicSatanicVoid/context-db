The folders hold two kinds of knowledge, in one format, and you read both the
same way.

  it applies to everything done in this repository.
- Usage knowledge is what a project tells agents in other projects about using
  it. When the instruction involves a project that this one uses, look for
  that project's usage folder among the background folders and under Global
  Context, and look into it before you read that project's code: it says what
  its users get wrong. This project's own usage folder, if Folders lists one,

  project is used.

A background folder is any other folder in `context-db/`, such as shared standards
or domain knowledge. Global Context, when that section appears below, lists
knowledge folders that are kept outside `context-db/`. One test applies to every
folder: open what bears directly on the instruction.

## How to use what you find

Context-db is a map, not the territory. Use it to orient, then verify against
the project's assets (code, code comments, configs, docs). Where they conflict,
trust the project's assets, especially code, and tell the user what is out of
date. The rule below says why, and what may be written here.

Do not run `/context-db prompt` yourself; the user invokes it. To consult
context-db again later in the session, navigate it the same way. Whether you may
write to it on your own is stated in the rules near the end of this output.

# How to Navigate Context-db

To see what a folder holds, run:

    python3 .claude/skills/context-db/context-db.py toc <folder>

It prints one line for each file and subfolder, with its description. This is
context-db's dynamic index: the listing is built every time it is asked for,
from the files as they are now, so it is never out of date. Use it every time
you look into a folder, now or later in the session, instead of listing the
folder, opening files to see what they are, or reading an `index.md` that the
folder may carry.

- Start with the project folder and the other folders listed under Folders.
- Open a file only when its description says it bears directly on the task.
- Run `python3 .claude/skills/context-db/context-db.py toc` on a subfolder only when its description does.
- Skip everything else. Reading widely dilutes what matters.
- Links inside a file are relative to that file.

# Context-db Is Not a Mirror of the Code

Context-db holds what an agent cannot learn by reading the project: why
decisions were made, conventions the code does not show, pitfalls, rules
imposed from outside, domain knowledge, and plans. Everything else already has
a home in the project's assets (code, code comments, configs, docs), and lives
there only.

A note that restates the project is a second copy. The copy drifts as the
project changes, nobody notices, and the next agent trusts it over the code.
So:

- Never write down what can be read from the project: file layouts, function
  signatures, CLI flags, what a function does, step-by-step walks through code,
  or anything a code comment, the README, or the docs already say. Link to it
  instead.
- A fact about one piece of code belongs in a comment next to that code, not in
  a note. Suggest the comment to the user instead of writing the note. When
  the fact is the reason for a decision, write the note too, so that the
  reason is not lost, and delete it once the comment is there.
- Where a note and the project disagree, trust the project's assets,
  especially code, and fix or delete the note. The exception is a note that
  says the code does not follow it yet: that is a requirement still to be
  built, not a stale note.

The test for every line: could an agent learn this by reading the project,
meaning its code, its comments, and its docs? If so, it does not belong in
context-db.

# Project Rules

This is a payments service and it is PCI-scoped. Before touching anything that
handles card data, storage, or logging, read
`context-db/acme-payments-project/pci-handling.md`. Do not infer the rules from
the code alone.

Write to the knowledge base only when the user runs `/context-db update`. At
any other time, leave `context-db/` alone. If you learn something worth keeping, say
so in one line and suggest that command.
